## 決定事項

### 1. 診断：伸びている軸と止まっている軸が、綺麗に分かれている

| 前倒しで伸びた軸 | 未着手のまま止まっている軸 |
|---|---|
| AI駆動開発 | マルチベンダー管理 |
| 仕組み・基盤構築 | 予算・見積もり・P/L |
| ドキュメント主筆 | 稟議・社内政治 |
| | 顧客との交渉 |

**左は全て「構造で殴れる領域」、右は全て「人・金・政治」。**

`base.md 第9章① 構造で殴れる問題しかやりたくなくなる（＝PMとして最大の落とし穴）` が現実化している。
しかも**成果が出ているため正当化されて気づけない**形で進行している。

そして3年後のゴールは「**取る・回す・利益出す**の全カバー」：

```
「回す」    → 現在やっている（得意領域）
「取る」    → 営業・提案・顧客交渉   ＝ 構造で殴れない
「利益出す」 → 予算・原価・P/L      ＝ 構造で殴れない
```

**3分の2が右側にある。得意軸をこれ以上伸ばしてもゴールには近づかない。**

### 2. 基本方針：AI軸は「目的」ではなく「通貨」として使う

自社は全社でAI推進中（cotomi / BluStellar）。**AI駆動開発の希少性には賞味期限がある**（数年で標準化する）。

> **AI軸をさらに積むのではなく、AI軸で貯めた信頼・認知を、右側の軸の獲得に交換する。**

17人が相談してくる状態＝**発言権を既に持っている**。その発言権をまだ一度も使っていない。

### 3. ★最大の地雷：「AI屋」でラベルが固定される

| 実態 | 周りから見えている姿 |
|---|---|
| 仕様統括 × AIリード | **AIの人** |
| 非機能要件・移行計画を主筆 | （AI以外の成果は見えにくい） |
| 17人展開・週次勉強会 | **圧倒的にこちらが目立つ** |

9月に新規参画者が増えると、**彼らの第一印象は「Claude Code を教えてくれる人」から始まる**。
そこで人数が増えるとラベルが確定し、**仕様の判断を求められなくなる**。
＝ 成長KPI「聞かれる質問の種類」が永久にツールの話のまま固定される。

#### 対策：9月の名乗り順を変える

新規参画者への自己紹介・体制図・パッケージ表紙のすべてで **「仕様統括」を先、「AI」を後** にする。

> ❌「AI推進担当の◯◯です。Claude Code の使い方は自分に聞いてください」
> ✅「**移行計画と仕様の統括をやっている**◯◯です。AI環境もこちらで整備しているので、そちらも聞いてください」

パッケージ層1の表題も「AI利用ガイド」ではなく **「案件オンボーディング（含AI環境）」** にする。

### 4. 6ヶ月の3フェーズ設計

本人の必勝パターン（Phase 1/2/3 で刻む ＝ thinking-os 新規2「段階的リリース戦略」）に乗せる。

| | 時期 | テーマ | やること | 取りに行く軸 |
|---|---|---|---|---|
| **Phase 1** | **9月** | **乗せる** | 作った仕組みに人を乗せ、**効果を人日で測る**。振り返りの場を自分で作り次の6ヶ月を合意 | 実績の数値化 |
| **Phase 2** | **10-11月** | **金に翻訳する** | 人日 → 金額に変換して報告。要員計画・見積もりの会話に入る。新規IF調整でベンダー折衝が発生 | **原価・見積もり** ＋ マルチベンダー |
| **Phase 3** | **12-2月** | **決める側に入る** | 「現行踏襲をどこで切るか」の論点を切り出し、**決定の場を作る** | 意思決定 |

### 5. 主軸は1本だけ：「見積もり・原価」

BUG-05（マルチタスクに弱い）のため、3軸同時には取りに行かない。

| 軸 | 扱い |
|---|---|
| **見積もり・原価** | **主軸。能動的に取りに行く** |
| マルチベンダー管理 | **発生するので受ける**（新規IF調整で自然発生。取りに行かない） |
| 意思決定の場 | **Phase 3 まで待つ**（Phase 1-2 の実績が権威の裏付けになってから） |

原価を主軸にする理由：

1. **権限ゼロで入れる唯一の軸**。数字を出すだけなので誰も止めない
2. **自分にしか出せない数字**（AI導入効果の試算はAIリードの領分）
3. **年収レンジの天井を決めている要素** — 4/09 の市場価値判定で本人が明記：
   「PLであってPMではない。**予算・P/L管理の経験が次の壁**」

#### ★入り方：「奪う」のではなく「供給する」

要員計画は案件PMが保持しており、ここは動かせない。したがって取りに行かず、供給する。

```
9月に人が増える → PMは要員計画を引く必要がある
    ↓
その時「AI環境で何人日削減できるか」は PM には出せない
    ↓
★ 自分にしか出せない数字
    ↓
渡す →「要員計画の前提に使ってください」
    ↓
要員計画の議論に呼ばれる ＝ 入場券
```

**奪えば越権、供給すれば支援。断る理由がない。** かつ自分の役割（仕様統括×AI推進）の範囲内に完全に収まる。

### 6. ★AI導入効果のベースライン取得（8月末まで／最重要タスク）

`2026-08-09` の**性能ベースラインと完全に同じ論理**が、AI導入効果にそのまま当てはまる。

```
9月に人が増えてパッケージを使い始める
    ↓
「立ち上がりが速くなった」と言いたい
    ↓
「パッケージ無しなら何日かかったか」の想定値が無い
    ↓
効果が主張できない ＝ 原価の会話に入る入場券を失う
```

**しかも人が入った後ではもう取れない。** 現行性能ベースラインと同一構造の不可逆タスク。

| 取る数字 | 取り方 |
|---|---|
| 参画者の立ち上がり想定日数（パッケージ無し） | 自分の実体験（6月の立ち上がり）＋ 既存メンバーに「この案件、把握するのに何日かかったか」を聞く |
| ドキュメント作成の想定工数 | 移行計画草案を書いた実工数（自分の実績があるので出せる） |
| ソース解析の想定工数 | 解析環境なしで人手でやった場合の想定 |

「既存メンバーに聞く」は **「新規参画者の立ち上がり計画を作っている」名目**で BUG-02 を迂回する（8/09 で確立した型の再利用）。

### 7. 振り返りの場は自分で作る（制度が無いため）

試用期間の面談は**制度として存在しない**ことが判明。向こうから評価は返ってこない。

主任が自分から振り返りの場を設計して持っていくのは、受け身より評価が高い
（minefield：案件PMは「何でも教えてください」スタンスを嫌う ＝ 自分で設計して持ってくる人を評価する）。

#### ★BUG-02 の突破口：口頭を文書に変換する

```
❌ 口頭で「面談させてください」と言う  ← ここで止まる（BUG-02）
✅ 3ヶ月の振り返りメモを1枚書いて先に送る →「これ、一度見ていただけますか」
```

**文書を送る行為は本人の得意技（主筆権の領域）。送った時点で場が発生し、切り出す勇気が不要になる。**
これは BUG-02 の汎用対処として今後も使える型。

#### 送るメモの構成（A4一枚）

| 項目 | 中身 |
|---|---|
| 3ヶ月でやったこと | `2026-08-16-contribution-audit.md` の10本をそのまま使える |
| 現状の役割認識 | アプリ仕様統括 × AI推進メイン、と自分は理解している（**認識合わせ**） |
| 次の6ヶ月でやりたいこと | 仕様と工数見積もりに軸足を移したい |
| **確認したいこと** | **この方向で合っているか** ／ 期待されている役割とズレていないか |

**「評価を求める場」ではなく「認識合わせ」の体裁にする。**
仕様統括が役割定義の認識を合わせるのは職務そのものであり、断られる理由がない。
ここが通ると、**その後の全行動が「上位者と合意した方向」として正当化される**（原価に踏み込んでも越権にならない）。

### 8. マルチベンダー管理は「これから」ではなく「既に渦中」

`2026-04-09-engineer-gap-analysis.md` では「マルチベンダー管理は未経験・埋めるのに6ヶ月〜1年」と評価していた。
しかし実際の体制は **計6社（客先2社／自社側4社）** であり、その中で**アプリケーション仕様を統括**している。

> 6社が関わる案件で仕様を統括することは、**構造的にベンダー間の仕様調整そのもの**。
> 責任分界の切り分け、課題の宛先決め、認識ズレの吸収は既に発生している。

→ **経験を積んでいるのに、経験として計上していない。**
BUG-06（得意技を0.3掛けで採点する癖）の別バージョン。「管理職として管理していないから未経験」と誤認しているだけ。

#### 対策：やっていることを、その名前で記録する

`docs/logs/` に書く際、「仕様の調整をした」ではなく
**「A社とB社の責任分界の論点を切り出して整理した」** と書く。
成長のためではなく **自己採点の分母を正すため**（実務は既に足りている）。

### 9. 「取る」は6ヶ月では捨てる（ただし隙間は1つある）

客先へのメイン説明は案件PMが保持。**客先の前に立てない構造**のため、営業・提案の軸は今回取れない。
3年ロードマップと整合する（「取る側」は Year 3）。**6ヶ月は「回す」＋「利益出す」に集中する。**

ただし例外：

> 「メイン説明はPM」＝ **メインは**、ということ。
> **仕様レベルの説明は仕様統括の領分**であり、非機能要件を客見せまでやった実績がある。
> **客先同席のサブポジションは取りに行ける。** Phase 2 で切り分けとして提案する。

### 10. 6ヶ月のKPI（BUG-06 対策として分母を先に固定する）

成長も定性で見ると「全然足りない」が再発する。**分母を今日決める。**

| 指標 | 現在（2026-08） | 2027年2月の合格ライン |
|---|---|---|
| **聞かれる質問の種類** | AIツールの使い方 | **仕様・移行方針の判断が月に数回来る** |
| **出席する会議の種類** | 作業・報告 | **意思決定の場に1つ以上定席** |
| 自分が論点を切り出して決めた数 | ほぼ0 | **累計3件** |
| 触った金額 | 0 | **要員計画 or 見積もりの一部に関与** |

**「劇的」ではなくこれが合格ライン。4つ中3つ埋まれば6ヶ月は成功。**
