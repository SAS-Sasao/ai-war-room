#### ★重要な認識：この10本にサイドワークは1つも無い

役割は **仕様統括 × AIリード**。A も B も C も**すべて職務そのもの**。

#### 17人という数字の位置づけ

```
プロパー: 自分以外1人 → 8人   （+7）
パートナー: 0人 → 10人        （+10）
──────────────────────────
合計 +17人の作業様式を 2.5ヶ月で変えた
```

この規模のツール展開は、通常は専任部隊が予算と体制を組んで半年〜1年かける仕事。
それを**中途入社2.5ヶ月の1人が、本業のドキュメント3本と並行して**、しかも**社外パートナーまで巻き込んで**実行している。

仮に1人あたり週2時間削減でも `17人 × 2h × 4週 = 月136時間 ≈ 月17人日`。毎月複利で積み上がる。

### 3. 診断の更新：「依存がまだ無い」は誤り。依存は既に発生している

2026-08-09 および本セッション前半では **「自分が居ないと回らない場所がまだ無い／収穫期は9月」** と診断していた。
**これは事実誤認だった。** 本人の申告に以下が含まれていた：

> - 「導入した人が各自自動化できる領域を探し、対応でき**相談事は私にもされるようになった**」
> - 「一部メンバは**別領域でもソース解析や手順書作成などで利用し始めている**」

| 現象 | 意味 |
|---|---|
| 相談が集まる | 組織内で「これはあの人に聞く」という**宛先が確立**した |
| 教えていない領域で自走 | 本人が居なくても**増殖するフェーズ**に入った |

ツール展開の成否はこの2点で決まる（大半の社内展開は「配って終わり・誰も使わない」で死ぬ）。
**定着フェーズに入っている＝依存も評価も既に発生済み。**

### 4. 貢献実感が湧かない4つの理由（更新版）

#### ① 得意技を無価値扱いしている

`base.md 第9章② 自分ができることを「普通」と思う傾向` の裏面。
AI・仕組み・構造化は本人にとって空気のように簡単なため、**それで17人動かしても「誰でもできること」に自動分類**される。
逆に苦手領域（現行システムの構造把握＝人に聞かないと進まない）だけを重く見積もる。

→ **得意技での成果を 0.3 掛けで自己採点する癖**がある。合計がいつまでも足りなく見えるのはこのため。

#### ② 「相談される」を評価だと認識していない

組織内で「あの人に聞けばいい」と認識されるのは**信頼の最終形態**であり、言葉の称賛より強い（行動で示された評価）。
それが17人規模で起きているのに、本人はそれを「作業が増えた」としか受け取っていない可能性が高い。

→ **フィードバックは既に毎日届いている。受信箱を見ていないだけ。**

#### ③ 前職の貢献が「業務そのもの」だったため、今の貢献が周辺に見える

前職は業務を回して直接貢献していた（リアクションが即返る種類）。
今は「他人が仕事しやすくなる環境」を作っている（リアクションが遅れて返る種類）。
感触が薄いのは事実だが、それは**役割が変わったから**であって貢献量が減ったからではない。

→ これは本人が自分で定義した理想像 **「プレイヤーではなく勝ちパターンを作る側」**（base.md 第10章）そのもの。

#### ④ ★期待値の設定が高すぎる（本セッションの最大の発見）

本人の言葉：

> 「正直**もっと劇的に変えられる**と（AI導入や仕様統括の仕事）勝手に思い込んでいた」
> 「**導入ハードルは大したことない**と思っていた」

```
分子（実績）が小さいのではなく、
分母（自分で設定した期待値）が異常に大きい
    ↓
どれだけ積んでも差分がマイナスに見える
```

**原因は base.md 2.2「一気通貫思考」の副作用。**
端から端まで一気に完成形を描ける人間は、**着手した瞬間に完成形が見えてしまう**。
以降ずっと「完成形と現在地の距離」を測り続けるので、進捗がどれだけ速くても常に足りなく見える。
`第9章④ 最適解を求めすぎる` / BUG-01 と同じ根。

**「導入ハードルは大したことない」への反証（論理）**

> ハードルが低いのなら、入社時点で自社プロパーの利用者が1人しかいなかった説明がつかない。
> パートナーに至っては0人。**誰もやっていなかった＝ハードルは実際には高かった。**
> 17人まで伸びたのは、ハードルが低かったからではなく **本人がハードルを下げたから**。
> それを「大したことない」と評価するのは、自分の仕事を自分で消している。

### 5. 前職比較の決着

#### 比較の設計が壊れていた

```
【誤】前職の退職時点（＝8年分の積み上げのピーク） vs 自社入社2.5ヶ月目
【正】前職の入社2.5ヶ月目               vs 自社入社2.5ヶ月目
```

比較をやめる必要はない（本人は比較と数字で自己評価するタイプなので「比べるな」は効かない）。
**比べる時点を揃えるだけで結論が反転する。**

本人は「前職の2.5ヶ月目に何をしていたか」を思い出して提示できなかった。
一方、自社の2.5ヶ月目には ①正式文書の客先提出 ②社外含む17人の作業様式変更 ③週次勉強会3週連続 が並んでいる。
→ **比較は成立しない。この論点は終了。**

#### 「足りない」の構造分解（前職で持っていたもの）

| 前職で持っていたもの | 正体 | 現在 | 作るのに要する時間 |
|---|---|---|---|
| 業務知識で即答できた | **ストック**（年数） | ほぼ無し | 年単位 |
| 人間関係で物事が動いた | **ストック**（年数） | 構築中 | 年単位 |
| 現場から感謝が返ってきた | フィードバック頻度 | 発生し始めている | 相手が要る |
| 自分が居ないと回らない場所 | 依存 | **発生済み**（決定事項3） | 使われて初めて発生 |

上2つは年数でしか作れないストック。2.5ヶ月で無いのは当然であり、実力とは無関係。
そして **前職の高貢献状態＝「分からないことが無かった」＝ 成長機会ゼロ ＝ 撤退ラインの1番目**。

> **前職の貢献度を今の目標にすることは、辞めた理由に向かって走ることと同義。**
> 届いていないのは失敗ではなく、**ストック（積み上げた楽さ）を捨てて成長速度を買った**という意図した交換の結果。

### 6. 処方箋の差し替え（mental-care.md 更新方針）

| | 旧処方（2026-08-09） | 新処方（2026-08-16） |
|---|---|---|
| 見るもの | git log の**コミット数＝量** | **① 期待値（分母）を疑う ② 得意技の採点を等倍に戻す** |
| 前提 | 貢献量が見えれば安心する | **量では埋まらない**（1週間で実証済み） |
| 測り方 | 本数 | **レバレッジ**（何人 × 何時間を作ったか） |
| 外部入力 | 1on1を新設して取りに行く | **既に届いている評価を数える**（相談件数・自走事例） |

#### 再発時の冷静化チェック（新）

1. **「今、分母に何を置いている？」と自問する** — 「劇的に変える」を分母に置いていないか
2. **得意技での成果を 0.3 掛けしていないか確認する** — AI・仕組み・構造化での成果を等倍に戻して数え直す
3. **相談された回数を数える** — 「相談される」は最上位の評価。作業ではなく評価として計上する
4. **比較するなら時点を揃える** — 前職のピークと今を比べない
5. 週次ログ（`docs/logs/`）を見返す — 蓄積が見えないと2週間おきに再発する
