### 1. 「貢献できているか」への回答（本丸）

#### 結論：貢献できているかで悩む段階は超えている

#### 実感が湧かない構造的理由（3つ）

**① 貢献の種類が「実感の返ってこないタイプ」に全振りされている**

非機能要件・移行計画・AI基盤・勉強会 — すべて **土台を作る仕事**。
土台は機能している間は誰も気づかず、壊れて初めて価値が分かる。

> 哲学「仕組みで勝つ。再現性で支配する」（base.md 第10章）の**構造的宿命**。
> 仕組みで勝つ人間は、勝っている最中に手応えが返ってこない。
> 貢献していないのではなく、貢献の種類が「後から効くタイプ」なだけ。

**② 欠損にだけ注意が向いている**

15台の構成が「なんとなく」であることばかり見て、書き上げた文書2本を勘定に入れていない。

**③ 既知のバグの再発**

`base.md 第9章③ 実力以上評価への不安` → 2026-05-31 Day0 で
**「評価への期待を裏切る恐怖」** として本丸特定済み。今回はその**現場版・続編**であり新規の問題ではない。

加えて、**3ヶ月目（9月）から伸びるのが当初プラン**。現在2ヶ月半で、むしろ前倒しで結果が出ている。

### 2. 現行システム理解の詰まり — 診断

#### 詰まりの正体は「知識不足」ではなく「再出力の欠落」

```
設計書は読んだ（インプットは通過している）
    ↓
「自分の言葉で再出力」していない
    ↓
想起できない ＝「なんとなく見たことある」で停止
```

本人の必勝パターンは **「読んだ情報を必ず3層/5柱/4象限で階層化して再出力する」**
（base.md 2.5 / 2026-04-10 に Deep Dive 3本 57KB を1日で書いた型）。
**今回だけそれを使っていない。** やり方を知らないのではなく、勝ちパターンの未適用。

未適用の理由：範囲が広く構造化の起点が決まらない（BUG-01）＋ 仕様統括とAIリードの並行処理（BUG-05）。

#### 認知の書き換え：仕様統括は「全部知っている人」ではない

| 誤 | 正 |
|---|---|
| 仕様統括＝15台すべてを理解している人 | 仕様統括＝**「誰が何を知っているか」を知り、論点を切り出して決める人** |
| 知識で勝つ | **構造と論点整理で勝つ**（本来の得意技） |

15台の詳細をすべて持っている人間はこの案件に一人もいない。断片を持つ生き字引が数人いるだけ。
**それを1枚に統合した者が勝つゲーム。**

#### 副作用の指摘：先生ポジションと生徒ポジションの衝突

AI領域で講師役を務めているため、**インフラ領域で「わかりません」と言いにくくなっている**。

→ 対処：**「教わる」形をやめ、「整理して持っていく → 添削してもらう」形にする。**
minefield の案件PM攻略法「質問は自分の仮説＋確認」と完全一致する。

### 3. この案件固有の「肝」— 3技術の掛け算で爆発する2箇所

U2L・FW刷新・DBバージョンアップは単体では定番だが、**同時に来ると掛け算で爆発する箇所**が生まれる。

#### ★肝①：文字コードが3層を貫通する

```
U2L（旧Unix系は EUC-JP / Shift-JIS が多い → RHEL は UTF-8 標準）
    ×
DB文字セット（JA16SJIS / US7ASCII → AL32UTF8）
    ×
Java層（旧FW時代のエンコーディング設定 → Spring Boot）
```

UTF-8化で **1文字のバイト長が変わる** → カラム長不足、固定長ファイルのズレ、外字・機種依存文字の欠落。
**3層のどこで化けたかの切り分けが極めて困難**。移行案件の炎上要因No.1。

#### ★肝②：性能劣化の原因が3層に分かれる

```
ハード変更（CPUアーキ変更 → シングルスレッド性能が変わる）
    ×
DB 19c（オプティマイザ変更 → 実行計画が変わる）★11g→19c の最大リスク
    ×
Spring Boot（コネクションプール・トランザクション境界の挙動差）
```

移行後に「バッチが夜間枠に収まらない」が発生した際、**原因が3つのどれか判別できず犯人探しで数週間溶ける**。
→ 決定事項4（性能ベースライン）の根拠。

#### その他の定番リスク（棚卸し用）

| 領域 | 肝 |
|---|---|
| U2L | エンディアン差（バイナリ／固定長ファイル）、ksh→bash のシェル互換、ジョブスケジューラ／帳票／監視ミドルのEOL |
| FW刷新 | **旧FW時代の"共通部品層"**（過去にベンダーが作った独自拡張）← 最大の地雷。画面数×遷移＝工数の全て、セッション依存 |
| DB | 廃止機能・非推奨パラメータ、PL/SQL資産量、移行方式（Data Pump / TTS）＝停止可能時間との勝負 |
| 全体 | **「現行踏襲」をどこで切るか** ← 仕様統括の本業。曖昧にすると後半で必ず揉める |

### 4. 性能ベースライン取得 — 「提案」ではなく「担当文書への1行追記」にする

#### 背景：移行案件で最も漏れやすい工程

移行案件の非機能要件では、性能要件を「現行同等以上」と定義するのが定番。
しかしこの書き方は、**現行の実測値が押さえられていて初めて検証可能になる**。
実測値の取得工程は、要件定義と移行設計の隙間に落ちやすく、後から気づいても取り返しがつかない。

#### 立て方の型（自分の担当文書に書き込む）

非機能要件が客見せ済み・レビュー中の段階では、「要件定義の欠陥指摘」として出すと自分の成果物を否定する形になる。
→ **移行計画草案（自分が主筆している文書）の移行前作業に1行入れる**形に格下げする。

> 移行前作業：**現行性能ベースライン取得**
> （主要バッチ処理時間 / 主要オンライン応答時間 / 主要SQL実行計画）

自分の担当文書に自分でタスクを書くだけなので、**政治コストがゼロ**。
**「提案」を経由せず工程を作れる**のが主筆権の最大の使い道。

#### 説明を求められた時の一言（型）

> 「非機能に『現行同等以上』で出しているので、比較対象の実測値がないと**移行後に達成判定ができない**。
> しかも**現行環境が現行のまま動いているうちにしか取れない**ので、工程に入れました」

- 非機能を書き切った本人しか気づけない論点＝権威がある
- 「約束の履行」であり指摘ではないので反対理由がない
- **不可逆性**が含まれるため後回しにされない

#### タイミングの原則

**レビュー期間中に出す。** レビューが閉じた後だと「後出し」になり出しづらくなる。

### 6. 新規参画者向けパッケージの設計

#### ★原則：「Claude Code の使い方」より「案件のコンテキスト」が10倍重要

ツールの使い方はネットにある。**案件のコンテキストはここにしかない。**
新規参画者が詰まるのは後者。講師役をしている反動で「使い方資料」に引っ張られるリスクが高いので意識的に抵抗する。

#### 3層構成

| 層 | タイミング | 中身 | 重要度 |
|---|---|---|---|
| **層1：入場** | Day 1 / 30分 | ・Bedrock + Claude Code セットアップ手順<br>・**★AI利用ガイドライン（やっていい／だめ）**<br>・リポジトリ構成 | **最優先・最も急ぐ** |
| **層2：文脈** | Day 1-3 / 本体 | ・**案件用 CLAUDE.md**<br>・**サーバー × 機能 × IF マトリクス**<br>・移行方針とスコープ（現行踏襲の境界）<br>・ドメイン用語集 | **最大レバレッジ** |
| **層3：型** | Day 3-5 | ・SKILL / サブエージェント一覧と使いどころ<br>・**やってはいけない使い方**<br>・検証ガードレール<br>・良い例／悪い例 | 中（**既存の週次勉強会コンテンツを流用可能**） |

#### 層2が最大レバレッジ

**案件用 CLAUDE.md の品質が、9月以降の全員の出力品質を規定する。**
1本のファイルで参画者全員分の生産性が決まる。ここに時間を集中投下する。
かつ **層2は移行計画草案を書く過程で自然に出来上がる**（決定事項5）。

#### 層1のガイドラインが最も急ぐ理由

**人が増えてからでは手遅れになる唯一の項目。**
判断基準が共有される前に人数が増えると、各自が個別に判断することになり、
機密・客先資料の取り扱いはその最たるもの。一度事故れば案件のAI推進そのものが止まる。
**他は後から直せるが、これだけは不可逆。** だから真っ先に着手する。分量はA4一枚でよい。

#### 層3は既存資産を流用

週次勉強会（金曜30分・SKILL化済み）のコンテンツが既に複数週分蓄積されている。
**層3はゼロから作らず再編集で済む** → 浮いた工数を層2に全投下する。

| 区分 | 作業の性質 | 手段 | 8月中のゴール |

#### 先行対応期間の最優先は「新規IFの本数と相手の確定」

1. 新規IFは**本数が固まるまで工数もスケジュールも引けない**＝移行計画の精度がここで決まる

知識の定着がなくても着手できる棚卸し作業のため、**詰まっている領域を迂回して成果が出せる**のも利点。

### 8. AI駆動の適用先（現行解析）

この案件は **Struts も Oracle も構造化された解析対象** のため、AI解析との相性が非常に良い。

| 解析対象 | 入力 | 出力（＝そのまま案件資産） |
|---|---|---|
| 画面・遷移の全量 | `struts-config.xml` / Action クラス | 画面一覧・遷移図・移行工数の根拠 |
| 業務ロジックの所在 | Action / Service クラス | 「どの機能がどこに実装されているか」マップ |
| DB依存 | SQL / PL/SQL | 19c 非互換候補リスト、実行計画要注意SQL |
| サーバー間連携 | 設定ファイル / hosts / FW定義 / ジョブ定義 | **IF一覧（プロトコル・データ形式・方向）** |
| 設計書の横断 | 既存設計書（大量） | サーバー × 機能 × IF マトリクス |

この動き方の強み：
- 「AI活用の実証」という大義名分がつくため**反対されない**
- **「知らないので教えてください」を一度も言わずに全体像が手に入る**
- 成果物が案件の共有資産になり、仕様統括の権威の裏付けになる
- 「読んで覚える」ではなく「**AIに出させて自分で検証する**」＝能動作業なので定着する
