## ⚠️ アプローチ変更（2026-08-09）

**旧方針**: 基礎（オンプレ／NW／TCP-IP）を先に学んでから案件の構成を理解する。期限は6月〜7月頭。
**結果**: 期限超過。進捗ログ・用語メモともに空欄のまま停止した。

### 停止した原因（診断）

TCP/IP の教科書を何冊読んでも、**担当システムのサーバー構成は1ミリも分からない**。
「どの機能がどのサーバーでどう実装され、どのプロトコル・データ形式でやり取りされているか」は
**その現場固有の情報**であり、基礎知識の量とは独立している。順番が逆だった。

さらに、設計書・構成図は読んでいたが **「自分の言葉で再出力」していない** ため定着していない。
（本人の必勝パターン ＝ 読んだ情報を階層構造で再出力する。今回だけ未適用だった）

### 新方針: 「学んでから作る」→「作りながら潰す」

```
案件の構造を成果物にする（サーバー × 機能 × IF マトリクス等）
    ↓
その過程で分からない用語・仕組みが出る
    ↓
その都度だけ潰す（下記「用語メモ」に放り込む）
    ↓
教材化して人に見せる → レビューで穴が埋まる
```

**基礎学習は「作業の副産物」として発生させる。単独の学習タスクとしては持たない。**

### 実行手段（2026-08〜）

- **成果物ドリブン**: 新規参画者向けオンボーディング資料（層2）＝現行システム構成の全体像。
  これを作ること自体が学習になる（「読んで覚える」→「教えるために書く」）
- **AI駆動**: 設定ファイル・ソース・ジョブ定義・設計書を Claude Code に解析させ、
  **出力を自分で検証する**形にする。受動的な読解ではなく能動的な検証にすることで定着させる
- **聞き方の型**: 「教えてください」ではなく
  **「新規参画者向けにまとめているのですが、認識合っていますか」**（bugs.md BUG-02 新発動形の対処）

## 1. 埋めるべき領域（棚卸し）

| 領域 | 現状 | 案件での用途（なぜ要るか） | 優先度 |
|------|------|--------------------------|--------|
| **サーバー間IF**（プロトコル・データ形式・方向） | 未把握 | 移行の肝。既存流用分と新規作成分の切り分け | **最高** |
| **文字コード**（EUC-JP/Shift-JIS → UTF-8、DB文字セット） | 未把握 | U2L × DB × Java層を貫通する最大の炎上要因 | **最高** |
| **ジョブ／バッチの依存と処理時間** | 未把握 | 移行後に夜間枠に収まるかの判定。性能ベースラインの対象 | 高 |
| オンプレミス環境全般 | 知識不足 | 主要クライアント案件の既存システム理解 | 高 |
| ネットワーク基礎 | 知識不足 | システム構成・体制の把握 | 中（都度潰し） |
| TCP/IP | 知識不足 | 上記の土台 | 中（都度潰し） |
| エンディアン差 | 未把握 | U2L でバイナリ／固定長ファイルに影響 | 中 |
| 塩漬けミドル（帳票／ジョブスケジューラ／監視）のEOL | 未把握 | 移行対象から漏れやすい。生き字引に聞くしかない領域 | 中 |
